# Prompt Guide for Graphics Generation

This guide contains detailed instructions and optimized prompt templates for AI
image generators (such as Imagen 2, Imagen 3, or similar) to create textures,
unit sprites, projectiles, and UI elements matching the Nintendo 64's visual
style and technical constraints.

**Note on how this fits the project:** TD64's active, in-game art is 100%
generated by code (`tools/gen_sprites.py`, `tools/gen_maps.py` — see
[README.md](README.md#asset-generation-tools)), not by AI image generation.
This guide is an optional alternative path for anyone who wants to replace
that procedural art with hand-illustrated or AI-generated art instead; if you
go this route, `tools/downsample_images.py` converts the result to the exact
dimensions and format the N64 build expects.

---

## 1. General Style and Technical Rules

For consistency across the whole game, make sure to include these technical
constraints in every prompt:

* **Style:** Retro 16-bit and 32-bit pixel art, late-90s console style.
* **Resolution:** Clean pixel grid, crisp and well-defined pixels (pixel-perfect). Avoid antialiasing filters, blur, modern soft gradients, or depth of field.
* **Background:** Pure black background (#000000) or a transparent background (alpha channel) for easy automatic cropping/extraction.
* **Perspective:** Top-down orthogonal view or isometric (45-degree downward camera angle) to fit the Tower Defense board.

## 6. Prompts for Animated Sprite Sheets

### Status: implemented

Every one of the 24 units now ships as an **8-frame animated sheet** rather
than a single static pose — the engine (`src/entities/animation.h` +
`src/entities/entities.c`) reads `frame_width` from each `AnimDef` and blits
the matching sub-rectangle of the sheet via `rdpq_sprite_blit`. The
procedural generator (`tools/gen_sprites.py`) already produces sheets in this
format for every unit. This section documents the exact format so that an AI
generator (or a hand-drawn replacement) can produce a compatible sheet for
any individual unit if you want to swap the procedural art for something else.

### Exact format the engine expects

**One sheet per unit**, a horizontal strip of **8 frames** in this fixed order
(matching `start_frame` in the code):

| Frames | Animation | Count | Loop |
|---|---|---|---|
| 0 | Idle | 1 frame | yes (holds) |
| 1–4 | Walk | 4 frames | yes |
| 5–7 | Attack | 3 frames | no (plays once, then returns to idle) |

- **Sheet size:** with a 32x32 base frame (the current unit size), the final
  sheet must be **256x32 px** (8 x 32), each frame occupying an exact 32px-wide
  cell. For projectiles (16x16) that would be 128x16 if animating them is ever
  worth doing, though it isn't a priority today.
- Frame 0 (idle) can be literally the single pose from Section 2 — no need to
  redo it, just insert it as the sheet's first cell.

### Prompting rules specific to animated sheets

In addition to the general rules in Section 1, when asking an image
generator for this:

1. **Ask for the whole strip in a single generation**, never frame-by-frame
   to stitch together afterward — models keep the character far more
   consistent (scale, angle, palette) when generating every frame together on
   one canvas.
2. **Be explicit about the grid**: "N-frame sprite sheet, single horizontal
   row, each frame in an equal-width cell, character perfectly centered and
   at the same scale/zoom in every cell" — this is the most important part:
   if the character "floats" or changes size between cells, the sprite will
   visibly jitter when animated in-game.
3. **Describe the pose sequence in order**, cell by cell, to guide the
   coherence of the movement cycle.
4. Keep the rest of Section 1's style rules (pixel art, no antialiasing,
   black or transparent background, orthogonal view).

### Prompt template (apply to all 24 units, swapping in the description/colors from Section 2)

> "Pixel art 32-bit, 8-frame character sprite sheet, single horizontal row, 8 equal-width cells of 32x32 pixels each, [UNIT DESCRIPTION AND COLORS — copy from Section 2], retro N64 game asset, black background, no antialiasing, orthogonal side view, character perfectly centered and at the same scale in every cell, consistent lighting across all frames. Sequence: cell 1 = idle standing guard pose facing right; cells 2-5 = walking cycle with alternating leg stride (contact, passing, contact opposite side, passing); cells 6-8 = attack cycle (windup, mid-strike, follow-through)."

**Applied example (Dawnguard Warrior / Crusader):**

> "Pixel art 32-bit, 8-frame character sprite sheet, single horizontal row, 8 equal-width cells of 32x32 pixels each, crusader knight in blue and gold plate armor holding a silver sword and a blue shield with a gold cross emblem, retro N64 game asset, black background, no antialiasing, orthogonal side view, character perfectly centered and at the same scale in every cell, consistent lighting across all frames. Sequence: cell 1 = idle standing guard pose facing right; cells 2-5 = walking cycle with alternating leg stride (contact, passing, contact opposite side, passing); cells 6-8 = sword attack cycle (windup raising sword, mid-swing strike, follow-through)."

### Technical pipeline to swap in a generated sheet

1. Generate the PNG (256x32 for 32px units) and save it, replacing the
   corresponding file at `assets/sprites/<faction>_<type>.png`.
2. In a pixel-art editor, check that every 32px cell is perfectly aligned —
   AI generators don't always respect the exact grid; fix by hand if needed.
3. `frame_width` in `src/entities/entities.c`'s three `AnimDef`s
   (`ANIM_IDLE`, `ANIM_WALK`, `ANIM_ATTACK`) is already `32`, matching this
   format — no code change needed unless the new sheet uses a different frame
   size. The `start_frame` values (0, 1, 5) are already correct too.
4. Rebuild (`make` / `libdragon make`). No need to touch `resources.c`,
   `mksprite`, or the `makefile` — the engine already reads `frame_width` at
   runtime via `rdpq_sprite_blit` with a sub-rectangle.
5. You can migrate unit by unit: a unit can keep `frame_width = 0` for a
   given animation and it will still draw as a single whole pose — it's not
   all-or-nothing.
6. Performance note: a 256x32 sheet in RGBA16 is 16KB, above the RDP's 4KB of
   TMEM — this isn't a problem because `rdpq_sprite_blit` automatically tiles
   the sprite in hardware; no extra code changes are needed.
